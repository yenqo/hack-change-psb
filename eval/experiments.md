## ⚠ Отложенная валидация: прогнать при получении golden set

10.11.2026 по решению команды протокол разово обойдён: три доработки реализованы заранее, одним коммитом, **без замеров**. Все за флагами, **по умолчанию выключены** — поведение решения строго как у v1.3 (golden master совпадает байт в байт). Принимать их нельзя, пока не прогнаны замеры ниже.

**Когда придёт `eval/golden.csv`:**

1. `python3 tools/check_golden.py eval/golden.csv` — замечания продактам; дождаться исправленного набора.
2. Калибровка шума: `python tools/eval.py calibrate --stage 3_stand` (3 прогона v1.3 + судья + повторная оценка без кэша) → порог в `eval/stand.md`; в журнал — строки v1.3 и v1.3 после рефакторинга.
3. **7.6** few-shot: прогон с `SOLUTION_FEWSHOT=fictional` → сравнение с принятой версией **только на вопросах вне few-shot**; проверка переноса фактов из примеров (числа, номера, названия «Кедр-Логистик», «Вектор-Снабжение» и т. п. в ответах). Остановка — решение команды.
4. **B3**: `python tools/b3_impact.py calib_v13_r1 calib_v13_r2 calib_v13_r3` — офлайн-масштаб на калибровочных ответах; затем прогон с `SOLUTION_FIX_DOCNUM=1` поверх принятого варианта few-shot. Остановка — решение.
5. **7.1**: `python tools/refcheck_eval.py` (точность проверки) и прогон с `SOLUTION_CHECK_REFS=1` поверх принятых 7.6 и B3. Остановка — решение.

Принятая доработка: флаг включается по умолчанию в `config.py`, тег `exp-…-accepted`; отклонённая — флаг остаётся выключенным.

### Гипотезы (записаны до замеров, 10.11.2026; после замера не правятся)

**7.6 — вымышленные few-shot** (`SOLUTION_FEWSHOT=fictional`; в правилах промпта образцы ссылок тоже заменены на вымышленные).
Меняется: 8 примеров из демо-вопросов → 8 примеров тех же типов (факт, нет в базе, ложная предпосылка, редакция на дату, внутренний документ, частичный ответ, диалог с уточнением, норма закона) на вымышленных документах; суммы, коды, названия и сроки не совпадают с базой (тест).
Влияет на: все вопросы; сильнее — на типы, по которым были примеры (premise, edition, partial, ambiguous/dialog).
Целевая метрика: итоговый балл вне few-shot — **не хуже** принятой версии в пределах порога (тогда выигрыш — честность оценки и отсутствие переноса фактов); на вопросах из few-shot ожидается падение (это ожидаемо и в решении не учитывается).
Защитные: доля выдуманных фактов (судья + авто), доля ложных отказов, средняя длина ответа.

**B3 — номера документов не проверяются как числа** (`SOLUTION_FIX_DOCNUM=1`).
Меняется: в проверке чисел номера вида «ПТ-05/2023», «К-12» вырезаются без учёта регистра.
Влияет на: ответы с номерами документов без «№» перед ними.
Целевая метрика: меньше лишних вызовов исправления и удалённых верных предложений (офлайн на калибровочных ответах); итоговый балл — без изменений или ↑. Предварительно (18 смоук-ответов): ложных срабатываний B3 не найдено — эффект ожидается небольшим.
Защитные: доля выдуманных фактов не растёт (проверка не должна пропускать настоящие выдуманные числа), время p95.

**7.1 — проверка номеров пунктов и документов** (`SOLUTION_CHECK_REFS=1`).
Меняется: ссылки ответа «п. X / ч. N / пп. N / ст. N / № …» проверяются по базе: пункт — в документе, к которому относится по тексту (или в другом упомянутом документе, или в контексте); номер документа — есть в базе; статья — есть в базе или упоминается ею. Неподтверждённые → в запрос на исправление; не помогло — предложение удаляется.
Влияет на: ответы с выдуманными пунктами/документами (редкие, но обнуляют балл).
Целевая метрика: доля ответов с выдуманными пунктами и документами ↓, итоговый балл ↑ или без изменений (доработка на безопасность: при «без значимой разницы» принимаем, если не ухудшила балл).
Защитные: доля ложных отказов, полнота ответов (длина, балл на fact/law), время p95, число вызовов LLM на вопрос.
Точность самой проверки (офлайн, `tools/refcheck_eval.py`, 10.11.2026): 25 реальных ответов модели — **0 ложных срабатываний**; 58 мутантов с выдуманными ссылками — поймано **52 (90%)**; пропуски — только пункт, существующий в другом упомянутом в ответе документе (12 из 18).

### 7.2 — готовый индекс (гипотеза и результат, 10.11.2026)

Меняется: эмбеддинги 336 фрагментов считаются заранее (`tools/build_index.py`, локальная bge-m3) и кладутся в `index_vectors.json` (float32 → base64, 1,8 МБ; в ZIP — 1,4 МБ) с отпечатком базы, хешем нарезки, моделью и размерностью. На старте при совпадении отпечатка и размерности 8 контрольных фрагментов эмбеддятся через API и сравниваются с сохранёнными: косинус ≥ 0,99 → готовый индекс, иначе — расчёт как в v1.3.
Цель: время старта ↓. Защита: ответы не меняются.
Результат: на dev-стенде расчёт эмбеддингов базы 27,9 c → 2,6 c (из них ~2,5 c — контроль через API); отличие компонент векторов ≤ 7·10⁻⁹, контрольный косинус 1,0. Golden master: с выключенным флагом — байт в байт; с готовым индексом из векторов заглушки — ответы, сообщения в модель и вызовы реранкера байт в байт, эмбеддинги базы не запрашиваются; при чужих векторах, другой базе или размерности — откат к v1.3 (тесты).
Риск на платформе: неизвестно, совпадёт ли её bge-m3 с локальной (ollama) с косинусом ≥ 0,99 — логов нет, проверить можно только косвенно. При несовпадении поведение = v1.3 плюс один вызов /embeddings на 8 текстов.
