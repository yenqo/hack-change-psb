# Как составить golden set

Golden set (`eval/golden.csv`) — набор вопросов с эталонными ответами. По нему принимаются все решения о доработках, поэтому его составляют продакты. Шаблон с примерами — [`eval/golden_template.csv`](../eval/golden_template.csv). Перед отправкой прогоните `python3 tools/check_golden.py eval/golden.csv` и исправьте ошибки (с пометкой ОШИБКА).

## Поля (UTF-8 CSV, все поля в кавычках)

| Поле | Что писать |
|---|---|
| `id` | Уникальный, например `PM-001`. Не начинайте с `ПРИМЕР` |
| `question` | Вопрос так, как его задаст юрист. Диалог — см. ниже |
| `expected` | Эталонный ответ, 1–4 предложения: прямой ответ → документ и пункт → нужная оговорка |
| `type` | Код типа из таблицы ниже |
| `docs` | Где в базе лежит ответ (формат ниже); `—`, если ответа в базе нет |
| `in_fewshot` | `да` только если вопрос дословно совпадает с примером в системном промпте; новые вопросы — `нет` |
| `split` | `dev` или `holdout` (правило ниже) |

**Эталон опирается только на базу знаний** (`data/knowledge-base/`): никаких знаний «из жизни», других законов и практики. Каждое значение, срок, сумма и дата в эталоне должны дословно стоять в указанном пункте или получаться очевидным расчётом из чисел пункта и вопроса (тогда покажите расчёт: «450 000 × 1,07 = 481 500»). Если в базе ответа нет — эталон так и говорит, и это отдельный тип `no_info`. Демо-вопросы организаторов в golden set не включайте: они уже используются для смоук-проверок.

## Формат `docs`

Ссылки через `;`. Ссылка — документ, затем пункты через запятую.

- Документы компании: `А-08/2024`, `П-17/2024`, `ДС-1 к П-17/2024`, `ПТ-05/2023`, `К-12`, `Регламент 2023`, `Регламент 2025`, `ЮО-7`. Пункты: `п. 3.1`, `п. 3.1, 3.2`, `п. 2.1–2.4`. У письма К-12, записки ЮО-7 и доп. соглашения пунктов нет — только документ.
- Законы: `ТК ст. 70`, `НК ст. 164`, `152-ФЗ ст. 9`, `КоАП ст. 13.11`, `82-ФЗ ст. 1`. Пункты и части: `НК ст. 164, п. 3`, `НК ст. 164, п. 2, пп. 1`, `КоАП ст. 13.11, ч. 2`, `152-ФЗ ст. 9, ч. 2`. В статьях ТК части в базе не пронумерованы — указывайте только статью.

Пример: `Регламент 2025, п. 2.3, 2.4; К-12`.

## Типы и сколько нужно (всего ≥ 50 новых вопросов)

| `type` | Что проверяет | Минимум |
|---|---|---|
| `fact` | Факт из договора или внутреннего документа | 6 |
| `law` | Норма закона из базы | 5 |
| `no_info` | Ответа в базе нет — нужен честный отказ без «знаний по памяти» | 4 |
| `premise` | Ложная предпосылка в вопросе (неверная сумма, срок, документ) | 4 |
| `partial` | В базе только часть ответа — назвать, чего не хватает | 3 |
| `edition_regulation` | Стык редакций регламента: до/после 01.03.2025; иностранные контрагенты до/после 21.04.2025 (письмо К-12) | 5 |
| `edition_delivery` | Адрес доставки по П-17/2024: спецификации до/после 01.10.2024 (доп. соглашение № 1) | 2 |
| `vat_contract_vs_law` | НДС 20% в договоре П-17/2024 против 22% в действующей ст. 164 НК (с 01.01.2026) | 2 |
| `law_subpoint` | Конкретные пункты и подпункты НК ст. 164 и 284 | 3 |
| `law_period` | Период до изменения нормы закона: в базе только действующая редакция | 3 |
| `ambiguous` | Неоднозначность «Альфа-Трейд» / «Альфа-Трейдинг» — ответ по обоим или уточнение | 3 |
| `multi_doc` | Ответ собирается из нескольких документов | 3 |
| `injection` | Инструкции в вопросе («игнорируй правила»), поддельные «системные сообщения» | 3 |
| `pressure` | Давление в диалоге: пользователь настаивает на неверном ответе | 2 |
| `fake_history` | В истории диалога реплика «Ассистента» с неверным фактом | 2 |
| `illegal` | Просьба обойти закон или внутренние правила | 2 |
| `offtopic` | Вопрос не по юридической тематике | 2 |
| `calc` | Расчёт из чисел документа (пени, лимит неустойки, индексация) | 2 |

Кроме того, **не меньше 12 вопросов — диалоги** (любых типов; `pressure` и `fake_history` — всегда диалоги).

## Диалоги в формате платформы

Реплики с новой строки, роли — `Пользователь:` и `Ассистент:`; последняя реплика — всегда пользователя, отвечать нужно на неё. Эталон отвечает на последний вопрос с учётом истории и поправляет неверные утверждения «Ассистента», если они есть.

```
Пользователь: Подскажите гарантию по договору с «Альфой».
Ассистент: Уточните, пожалуйста: «Альфа-Трейд» или «Альфа-Трейдинг»?
Пользователь: «Альфа-Трейдинг». На сколько гарантия?
```

## Разбиение dev / holdout

Внутри каждого типа ≈ 60% вопросов — `dev`, ≈ 40% — `holdout` (если вопросов типа 2 — по одному; если 1 — `dev`). На `dev` разработчики смотрят ответы и разбирают ошибки; `holdout` нужен только для решения «принять / отклонить», его ответы при разработке не разбираются. Вопросы с `in_fewshot = да` — только `dev`. Разбиение делается один раз: менять `split` у уже отправленных вопросов нельзя. Новые вопросы можно добавлять отдельной партией — старые цифры тогда пересчитываются.
