## 2. Временный протокол замеров (пока нет golden set)

Golden set от продактов ещё не готов. До его появления задачи R4–R7 меряются **предварительно на 18 демо-вопросах**. Это слабый замер, и его нужно делать честно.

### 2.1. Что учитывать
- **Few-shot в текущем промпте содержит 8 демо-вопросов с ответами.** Эти вопросы в замерах не учитываются: основная метрика — по остальным 10 демо-вопросам. Балл по всем 18 — только справочно.
- **10 вопросов ловят только большие эффекты.** Поэтому замер состоит из трёх частей (раздел 2.3), а не из одного итогового числа.

### 2.2. Калибровка шума на демо (один раз, перед R4)
- Прогони текущую принятую версию (раздел 0) на 18 демо-вопросах **3 раза** с выключенным кэшем чата. Судья и baseline — как на стенде.
- Посчитай: разброс балла по 10 вопросам вне few-shot; для каждого вопроса — менялась ли оценка между прогонами («нестабильные вопросы»).
- Запиши в `eval/stand.md` раздел «Временный стенд: демо» с порогом шума и списком нестабильных вопросов.
- Сохрани ответы и контексты калибровки: на них работает R1.

### 2.3. Замер каждой задачи R4–R7
1. **Гипотеза до запуска** — в `eval/experiments.md`: что меняется, на каких вопросах должен быть эффект, целевая и защитные метрики.
2. **Прогон на демо** с флагом: 2 прогона (кэш чата выключен), сравнение со средним калибровки.
3. **Целевые сценарии.** Для каждой задачи — 3–6 коротких сценариев, на которых эффект должен проявиться (описаны в разделе 3). Пометь их как «сценарии агента»: это проверка, что механизм работает, а не оценка качества. В golden set их не добавлять.
4. **Регрессии.** Список демо-вопросов, у которых оценка ухудшилась хотя бы в одном прогоне, с причиной. Если в каком-либо ответе появился выдуманный факт, которого не было в калибровке, — это стоп-сигнал.
5. **Офлайн-проверки** там, где они возможны без вызова модели (на сохранённых ответах и контекстах калибровки).

### 2.4. Правило решения (предлагаешь ты, решаю я)
- **Предварительно принять:** целевые сценарии проходят; на 10 вопросах вне few-shot нет ухудшения больше порога шума; нет новых выдуманных фактов; защитные метрики (время, доля кэша, размер контекста) в норме.
- **Отклонить:** любой новый выдуманный факт, регрессия больше порога шума или нарушение защитных метрик.
- Предварительно принятая задача: флаг **включается по умолчанию**, тег `exp-NN-prelim`.
- **Когда появится golden set:** все предварительно принятые задачи перемеряются по полному протоколу из основного задания (раздел 8.3). Для этого каждая задача должна отключаться своим флагом независимо от остальных.

## 3. Задачи

### R1. Диагностика (без изменения ответов)
Всё — на сохранённых ответах и контекстах калибровки (раздел 2.2), без новых вызовов модели. Сделай из этого инструмент `tools/diagnose.py`, чтобы потом прогнать его на golden set.

**(а) Поиск.**
- Для каждого демо-вопроса: какие документы и пункты ушли в контекст; попали ли нужные (по эталонам из таблицы в основном задании, раздел 8.1; в golden set — по полю `docs`); на какой позиции оказался нужный фрагмент закона до и после реранкера.
- Для вопросов с баллом ниже 0,5 — причина: «нужного фрагмента не было в контексте» (поиск) или «был, но ответ неверный» (генерация).
- Работал ли реранкер локально (на платформе он есть).

**(б) Выдуманные факты.** Один выдуманный факт обнуляет балл за вопрос, поэтому это главный кандидат на причину низкого балла.
- Для каждого ответа: числа, сроки, суммы, проценты, даты, номера пунктов и документов, которых **нет в эталоне** — кандидаты на «выдуманный факт» в глазах судьи, даже если они есть в базе. Отдельно: каких **нет и в контексте** — настоящие выдумки.
- Сколько ответов судья оценил как «значительно хуже» (0) и есть ли в них такие кандидаты.

**(в) Длина ответов.**
- Распределение числа слов в наших ответах и в ответах стартового примера; доля наших ответов длиннее 150 слов (рекомендация регламента).
- Есть ли связь между длиной ответа, числом фактов сверх эталона и оценкой судьи.

**Отчёт:** какая доля ошибок от поиска, какая от генерации; сколько ответов содержат факты сверх эталона и выдумки; связь длины с оценкой. От этих выводов зависит, насколько полезны R6 и R7. Если окажется, что длинные ответы с лишними фактами систематически проигрывают, предложи в `eval/backlog.md` гипотезу «краткий режим ответа» (короткий вывод + 1–2 ключевых пункта со ссылками, ~80–120 слов). Сам не начинай.

### R3. Поле `context` для веба (без изменения ответов)
Веб должен видеть, какие документы и фрагменты ушли в контекст модели.
- В `Result.to_dict()` — поле `context`: по каждому документу `doc_id`, название, вид, `included` (`whole` / `fragments`), `reason` (`company_full`, `search`, `related`, `date_applicable`, `short_article`, `general_point`, позже `cross_ref` из R6), для `whole` — `search_hits` (пункты, найденные поиском, со смещениями и рангом), для `fragments` — список фрагментов (`clause`, `start`, `end`, `rank`, пометка редакции), `applies_to_event_date`, `cited` (сослался ли ответ). Плюс `date_note` и `removed_from_context` (вырезанные инструкции со смещениями).
- **Тексты не передавать** — только идентификаторы и смещения; текст веб берёт через `get_document`.
- Собирать `context` **из тех же объектов, из которых строится сообщение модели**, а не пересчитывать отдельно.
- В `kb.py` сохранять у каждого фрагмента `start` / `end` в исходном тексте документа (в том, который возвращает `get_document`), даже если в текст фрагмента дописываются пометки.
- **Тесты:** для каждого элемента `context` `text[start:end]` совпадает с исходным куском; каждый фрагмент из `context` присутствует в отправленном сообщении (на заглушках); ответы в CSV и golden master не изменились.
- Подними `CONTRACT_VERSION`, обнови `docs/integration.md` и примеры, отметь строкой «изменение для веб-разработчика».

### R4. Даты доп. соглашений, писем и редакций законов (раздел 7.3)
- Извлекать дату начала действия и условие применения у документов, которые меняют или дополняют другие: письмо К-12 дополняет п. 5.4 Регламента ред. 2025 с 21.04.2025; Доп. соглашение № 1 меняет п. 3.2 П-17/2024 для спецификаций, подписанных после 01.10.2024. Учитывать их в справке по датам **с условием**, а не только с датой.
- Для пунктов законов с пометкой «изменен с <дата>»: если дата события раньше — добавлять в справку «в базе только действующая редакция ст. N, п. M; на дату события могла действовать иная».
- Справка — после неизменной части запроса (кэш провайдера).
- **Целевые сценарии:** иностранный контрагент до и после 21.04.2025; адрес доставки по спецификации от сентября и от ноября 2024; ставка НДС для поставки 2024 года (в договоре 20%, в действующей ст. 164 — 22%, прежней редакции в базе нет); договор на 12 млн в августе 2024 и в мае 2025.
- **Защита:** остальные демо-вопросы, время, доля кэша.

### R5. Противоречие между выводом и обоснованием (B2)
На демо-вопросе 5 ответ начинался с «Нет.», а обоснование говорило, что одобрение было нужно.
1. **Сначала частота.** На сохранённых ответах калибровки посчитай, как часто первое «Да» / «Нет» расходится с обоснованием (эвристика по первому слову + ручная проверка найденных случаев). Покажи цифру.
2. **Затем самое лёгкое исправление**, по возрастанию стоимости:
   - (а) правка системного промпта: вывод формулируется после сверки с найденными пунктами, первое слово обязано совпадать с итогом обоснования;
   - (б) если (а) не помогло — условная самопроверка: только для ответов, начинающихся с «Да» / «Нет», короткий вызов модели «согласуется ли первое слово с обоснованием», при расхождении — исправление. Общая часть этого вызова — в начале запроса (кэш).
3. **Целевые сценарии:** вопрос 5 и 3–5 похожих вопросов «нужно ли было…» с ответом «да» и с ответом «нет».
- **Защита:** время (для варианта (б) — доля вопросов, где сработала самопроверка, прирост p50/p95), остальные демо-вопросы.

### R6. Расширение по ссылкам внутри законов (B4)
- При индексации разбирать отсылки в пунктах законов («пункт N настоящей статьи», «подпункт N пункта M», «статьей N настоящего Кодекса / Закона») и сопоставлять их с фрагментами базы. В НК ст. 164 и 284 таких отсылок больше сотни, в документах компании — единицы (их и так видно целиком).
- После отбора законов добавлять фрагменты, на которые ссылаются выбранные: на 1 шаг, не больше 3, в пределах текущего бюджета законов; помечать «[упомянут в п. …]».
- Для отсылок на статьи, которых нет в базе, добавлять строку «ст. N … в базе отсутствует» (пример: 152-ФЗ ст. 9 ссылается на ст. 6, 10, 11, которых в базе нет).
- В `context` для веба — `reason: cross_ref`.
- **Целевые сценарии:** 3–5 вопросов по подпунктам НК ст. 164 и 284, где ответ требует пункта, на который ссылается найденный; демо-вопрос 13 (152-ФЗ).
- **Перед реализацией** посчитай по R1, сколько вопросов вообще затрагивают такие отсылки. Если в демо их почти нет — скажи; попросим продактов добавить такие вопросы в golden set.
- **Защита:** остальные вопросы, размер контекста, время, доля кэша.

### R7. Облегчённое переформулирование запроса (облегчённый 7.7)
- Вызов LLM **только** когда он вероятно нужен: вопрос содержит историю диалога, или поиск по законам вернул слабый результат (порог по лучшему скору — подобрать по калибровочным прогонам и R1).
- Вход: история и вопрос, **без документов**. Выход (JSON): самостоятельная формулировка вопроса и 2–3 поисковых запроса. Системный промпт постоянный (кэш провайдера).
- Поисковые запросы идут в гибридный поиск вместе с исходным вопросом (слияние через RRF); в сообщение модели для ответа добавляется самостоятельная формулировка — **после** неизменной части запроса.
- Новый вызов должен вписаться в логику уровней B7/B8: при нехватке времени он пропускается первым.
- **Целевые сценарии:** демо-вопросы 6, 15–18 (диалоги); 3–5 бытовых формулировок по законам («главбуха на испыталку на сколько можно взять»).
- **Защита:** доля вопросов, где сработал вызов; задержка одного ответа p50 / p95 (важно для веб-чата); выдуманные факты; результат `tools/fault_eval.py` (доля ответов на полном уровне не должна упасть).

## 4. Общие правила этого раунда

- **Одна задача — один флаг — один коммит — одна остановка.** Не начинай следующую задачу до моего решения по предыдущей.
- Каждая задача R4–R7 отключается своим флагом независимо от остальных.
- После каждой задачи, меняющей ответы, прогоняй `tools/fault_eval.py`: исправления устойчивости B5–B8 не должны пострадать.
- Всё переменное — **после** неизменной части запроса; в отчётах — доля входных токенов из кэша (`prompt_tokens_details.cached_tokens`).
- Бюджет: до 10 млн токенов на задачу; в отчёте — сколько потрачено на задачу и всего.
- Сценарии агента и демо-замеры — только для предварительных решений. В golden set их не переносить.
- Новые идеи — в `eval/backlog.md` с гипотезой, сам не начинай.
- Сабмит на платформу — только по моей просьбе; перед сабмитом покажи включённые флаги и состав архива из `tools/make_submission.py`.
- Пиши отчёты на русском.

### Формат отчёта после каждой задачи
1. Что сделано (коммит, флаг).
2. Для R1 и R3: подтверждение, что ответы не изменились (golden master), и результаты задачи.
3. Для R4–R7: гипотеза; балл по 10 вопросам вне few-shot (калибровка против задачи, с порогом шума); результаты целевых сценариев; регрессии по вопросам с причинами; выдуманные факты; время p50 / p95; доля кэша; результат `fault_eval`; токены.
4. Предложение: предварительно принять / отклонить — и почему.
5. Строка «изменение для веб-разработчика», если затронут фасад.
