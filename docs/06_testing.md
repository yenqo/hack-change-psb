# 06. Тестирование

Ключа к прокси платформы у нас нет, а логов платформа не показывает. Поэтому решение проверяется локально двумя способами:

- **без ключа:** поиск, проверка чисел и заглушка прокси, которая имитирует сбои платформы;
- **с ключом DeepSeek:** чтение реальных ответов модели.

Инструменты лежат в отдельном необязательном архиве `psb_test_kit.zip`. Распакуйте его в корень репозитория рядом с `solution.py` — появятся папки `tools/` и `data/`:

```
solution.py
tools/          проверки, заглушка прокси, локальный прогон, сборка ZIP
data/
  knowledge-base/       21 документ базы (материалы организаторов)
  demo_questions.csv    18 демо-вопросов
  demo_output.csv       эталонные ответы к ним
```

`data/` — материалы организаторов. Репозиторий с ними должен быть приватным.

**Что нужно:**
- Python 3.10+ и `bash`;
- `pip install httpx==0.28.1`;
- для теста стеммера — `pip install snowballstemmer`;
- для прогона на модели — утилита `zip`.

## Полный набор проверок без ключа (~5 минут)

```bash
tools/run_all_tests.sh
```

Запускать перед каждым сабмитом. Набор готовит `testdata/` (архив базы в двух вариантах и наборы вопросов), затем выполняет:

| Проверка | Что проверяет | Ожидается |
|---|---|---|
| `test_stemmer.py` | Наш стеммер против эталонного `snowballstemmer` на всех словах базы | 0 расхождений из 4153 |
| `eval_retrieval.py` | Попадает ли нужная статья или пункт закона в контекст. 20 вопросов, только BM25, без эмбеддингов и реранкера | 20/20 |
| `test_numbers.py` | Проверка чисел: ложные срабатывания на 18 эталонах `demo_output` и поимка 5 подложенных ошибок (7 рабочих дней вместо 5, «90 дней», выдуманная редакция и т. п.) при пропуске 2 верных расчётов | 0/18 ложных, все 7 случаев OK |
| Сценарии против заглушки | Весь прогон `solution.py` при разных сбоях прокси; каждый `submission.csv` проверяется `validate.py` | Все OK; запасные ответы только в сценарии «модель недоступна» |

| Сценарий | Что имитирует | Время | Результат |
|---|---|---|---|

| 30% ошибок 429/503 | Нестабильный прокси | 8,8 с | OK, 0 |

| неверные форматы ответов | Эмбеддинги и реранкер возвращают мусор | 0,8 с | OK, 0 |

| 503 первые 30 с | Модель «загружается» | 31,8 с | OK, 0 |
| прокси поднимается через 60 с | Именно та ситуация, что обнулила v1 и v1.2 | 63,1 с | OK, 0 |

В `slowembed` решение закончило работу за 62 с, но процесс завершился на 84-й секунде: интерпретатор ждёт зависшие запросы эмбеддингов до их тайм-аута (20 с). В бюджет это укладывается.

Сравнение с v1.2 на сценарии «прокси поднимается через 60 с»: v1.2 сдаётся через 33 с с 18 запасными ответами. Так мы и нашли причину баллов 20,77.

## Заглушка прокси

`tools/mock_proxy.py` — OpenAI-совместимый сервер с эндпоинтами `/chat/completions`, `/embeddings` и `/rerank`. Ответы модели здесь фиктивные: заглушка проверяет поведение решения при сбоях, а не качество ответов. На вопросы о качестве товара она нарочно выдумывает срок «7 рабочих дней», чтобы сработали проверка чисел и исправление.

```bash
tools/run_scenario.sh <режим> <набор> [бюджет_сек] [потоков]
# пример: прокси с 30% ошибок, 300 вопросов, бюджет 10 минут, 2 потока
tools/run_scenario.sh flaky testdata/big300 600 2
```

**Режимы** (можно несколько через запятую):

| Режим | Поведение |
|---|---|
| `ok` | Всё работает |
| `flaky` | 30% запросов — 429 или 503 |
| `down` | Генерация всегда 500 |
| `no_aux` | Эмбеддинги и реранкер — 404 |
| `badfmt` | Эмбеддинги и реранкер — неверный формат |
| `slow` | Генерация 4 с |
| `latency` | Время генерации растёт с длиной запроса (1 с + 1 с на 15 000 символов) |
| `slowrerank` | Реранкер 20 с |
| `slowembed` | Эмбеддинги 25 с |
| `warmup` | Первые 30 с всё отвечает 503 (`MOCK_WARMUP` меняет длительность) |

**Наборы:** `testdata/flat` (18 демо-вопросов, плоский архив), `testdata/folders` (то же, архив с папками), `testdata/big300` (300 вопросов — проверка уровней обработки по времени).

**Переменные:**

| Переменная | Что задаёт |
|---|---|
| `MOCK_MAX_TOKENS` | Предел `max_tokens` |
| `MOCK_MAX_CHARS` | Предел длины запроса |
| `MOCK_CONC` | Предел одновременных запросов (выше — 429) |
| `MOCK_DELAY` | Запуск заглушки через N секунд |
| `SOL` | Какой файл решения проверять (по умолчанию `solution.py`) |
| `TOK` | Значение `MAX_TOKENS`, которое «передаёт платформа» |

Результаты сценария лежат в `runs/<режим>-<набор>-<решение>/`: `submission.csv`, `stderr.log` (лог решения), `mock_stats.json` (что заглушка получила: число вызовов, максимальный размер запроса, `max_tokens`, модели).

## Прогон на настоящей модели

Это главный способ понять качество ответов (P0 в [плане](05_roadmap.md)).

```bash
DEEPSEEK_API_KEY=sk-... tools/run_local.sh
```

Скрипт:
1. собирает в `runs/local-deepseek/` архив базы и 18 демо-вопросов;
2. запускает `solution.py` на API DeepSeek (`https://api.deepseek.com`, модель `deepseek-chat`) с `SOLUTION_DEBUG=1`;
3. пишет два файла:
   - `runs/local-deepseek/compare.txt` — по каждому вопросу: вопрос, наш ответ с числом слов, эталон;
   - `runs/local-deepseek/debug.jsonl` — по каждому вопросу: уровень обработки, какие законы и документы попали в контекст, справка по датам, черновик, неподтверждённые числа, итоговый ответ, размер запроса.

Другой OpenAI-совместимый сервис задаётся через `LLM_BASE_URL` и `LLM_MODEL`. У API DeepSeek нет `/embeddings` и `/rerank`, поэтому решение само перейдёт на BM25.

**Ключ передаётся только через переменную окружения.** Ни в код, ни в файлы репозитория его не записывать.

## Вспомогательные скрипты

| Скрипт | Для чего |
|---|---|
| `tools/show_prompt.py 5 17` | Печатает системный промпт и запрос к модели для демо-вопросов 5 и 17, а также статистику размеров запросов |
| `tools/inspect_kb.py` | Как решение разобрало базу: тип, статус, число фрагментов каждого документа. С аргументом-подписью печатает текст фрагмента |
| `tools/compare.py q.csv sub.csv [gold.csv]` | Вопрос, наш ответ и эталон рядом |
| `tools/validate.py q.csv sub.csv` | Формат `submission.csv`: заголовок, `id`, пустые и слишком длинные ответы, BOM, число запасных ответов |
| `tools/make_submission.sh v1.4` | Собирает `dist/psb_submission_v1_4.zip` из `solution.py` и `requirements.txt` и сохраняет копию кода в `submissions/v1.4/` |

## Запуск без набора инструментов

```bash
mkdir -p data && cp /путь/к/knowledge-base.zip /путь/к/questions.csv data/
DATA_DIR=data LLM_BASE_URL=https://api.deepseek.com LLM_API_KEY=$DEEPSEEK_API_KEY LLM_MODEL=deepseek-chat \
  SOLUTION_DEBUG=1 python3 solution.py
# результат: submission.csv и debug.jsonl в текущей папке, лог — в stderr
```

## Перед каждым сабмитом

1. `tools/run_all_tests.sh` — всё OK.
2. Если менялся промпт или логика ответа — `tools/run_local.sh` и просмотр `compare.txt`.
3. `tools/make_submission.sh vX.Y` — архив и копия кода.
4. Строка в [журнале](04_experiments.md#сабмиты): версия, одно изменение, гипотеза.
