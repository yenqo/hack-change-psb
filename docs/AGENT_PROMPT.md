# Задача для ИИ-агента: реструктуризация и доработка юридического ассистента ПСБ (Hack&Change 2026)

Ты — опытный Python-разработчик и инженер RAG-систем. В репозитории уже есть рабочее решение `solution.py` (версия v1.3, результат на лидерборде из шапки файла — 24,652) и разные сопутствующие файлы. Твоя задача:

1. разобрать и упорядочить репозиторий;
2. разложить `solution.py` на модули по целевой архитектуре **без изменения поведения**;
3. по одной добавить недостающие доработки, каждую — с проверкой на метриках;
4. подготовить ядро к интеграции с веб-интерфейсом: стабильный программный интерфейс, JSON-контракт, контрактные тесты и документацию для веб-разработчика;
5. сделать инструменты оценки и документацию ядра.

**Веб-интерфейс делает другой член команды. Ты его не пишешь и не меняешь:** не создаёшь API-сервер, фронтенд, Dockerfile и compose для прототипа и не трогаешь файлы веб-части, если они есть. Твоя зона — ядро, сабмит, оценка и интеграционный контракт (раздел 9). Хорошая интеграция означает, что веб-разработчик может подключить ядро по документации, не читая его код.

Работай поэтапно (раздел 11). После каждого этапа запускай проверки и коротко отчитывайся: что сделано, что проверено, какие метрики, что дальше. **Главное правило: ничего не должно стать хуже, чем v1.3.**

## 2. Жёсткие ограничения (нарушать нельзя)

### Платформа автопроверки
- Запускается **только** `solution.py` в Docker. Отдельных сервисов нет.
- В ZIP-сабмит попадают **только корневые `.py`-файлы, `requirements.txt` и файлы индекса в корне архива**. Всё, что импортирует `solution.py`, — плоские модули в корне репозитория. Никаких пакетов в подпапках для кода ядра.
- **Зависимости ядра: только `httpx==0.28.1` и стандартная библиотека.** Нельзя: numpy, pydantic, pymorphy, rank_bm25, langchain, openai SDK. `pip install` из кода запрещён.
- 8 CPU, 16 ГБ RAM, **20 минут на весь прогон**, ZIP ≤ 128 МБ, 5 сабмитов в день.
- Вход: `$DATA_DIR/questions.csv` и `$DATA_DIR/knowledge-base.zip`, `DATA_DIR` по умолчанию `data`.
- Выход: `submission.csv` в рабочем каталоге, UTF-8, ровно `id,answer`, все ID, без дублей, ответы непустые, ≤ 10 000 символов, стандартное CSV-экранирование. Рекомендуемая длина ответа — до 150 слов.
- Вопрос может содержать историю диалога (`Пользователь: … / Ассистент: …`). Отвечать на последнюю реплику пользователя. Состояние между ID не переносится.

### Модели и доступ
- Один OpenAI-совместимый прокси: `/chat/completions` (модель из `LLM_MODEL` / `OPENAI_MODEL` / `GEN_MODEL`, на платформе — DeepSeek V4.1 Flash), `/embeddings` (`EMB_MODEL`, bge-m3), `/rerank` (`RERANKER_MODEL`, на платформе — Qwen3 Reranker 8B, необязателен).
- Адрес, ключи и параметры — только из окружения, как уже сделано в v1.3. Имя модели не хардкодить.
- **Ключи не хранить в коде, файлах, логах и коммитах.** Только `.env.example` с пустыми значениями.

### Содержательные
- Знания модели и внешние источники для обоснования ответа использовать нельзя.
- Нельзя выдумывать документы, пункты, суммы, сроки. **Один выдуманный факт обнуляет балл за вопрос.**
- Оценка: LLM-судья сравнивает ответ с baseline, ориентируясь на эталон, в двух порядках A/B, шкала 0–1; итог = 0,7 × Match Rate + 0,3 × Win Rate. Экспертная часть: работоспособность 20%, контроль достоверности 25%, архитектура 20%, скорость 15%, интерфейс 15%, презентация 5%. Без работающего веб-чата решение не допускается к экспертной оценке.

## 3. Что уже есть в `solution.py` v1.3

Перед изменениями прочитай файл целиком и убедись, что понимаешь каждую часть. Кратко:

- **Конвейер на вопрос — один вызов LLM.** В контекст идут все документы компании целиком, найденные пункты законов, справка по датам и история диалога. Затем проверка чисел кодом, при необходимости один вызов на исправление, затем удаление предложений с неподтверждёнными сроками и датами.
- **Загрузка базы:** ZIP или папка, TXT/MD/CSV/DOCX, кодировки utf-8/cp1251, имена файлов из ZIP с macOS и Windows, пропуск мусорных файлов.
- **Санитизация** встроенных инструкций для ИИ (в служебной записке ЮО-7 такая есть) — строка заменяется пометкой.
- **Метаданные документов компании:** «утратил силу с», «действует с», «редакция от» → `valid_from`, `valid_to`, `status`.
- **Законы:** статья, акт, название; нарезка по пунктам и подпунктам до 1 600 символов; редакционные пометки Гаранта выделены как `[Пометка редакции: …]`; к статьям НК добавлено название налога по главе.
- **Поиск:** свой стеммер Snowball, BM25, словарь синонимов, dense-векторы bge-m3 (считаются при каждом запуске, до 60 с), RRF, реранкер с автоотключением, правила подбора законов (короткие статьи целиком, общие пункты больших статей, уменьшение бюджета для вопросов о документах компании).
- **Даты:** извлечение периода из вопроса (даты, месяц и год, год) → справка «применимы / не действовали» по датам действия документов.
- **Связанные документы** (договор ↔ доп. соглашение, регламент ↔ письмо, редакции) — используются в компактных режимах.
- **Системный промпт** с правилами контроля достоверности и 8 few-shot примерами в трёх вариантах длины. **Примеры взяты из демо-вопросов.**
- **Проверка чисел:** числа цифрами и словами, единицы измерения, числа, получаемые расчётом. **Номера пунктов и документов перед проверкой вырезаются и не проверяются.**
- **Надёжность и время:** запасной ответ (лучший фрагмент базы) с первых секунд, перезапись CSV через временный файл, общий дедлайн, уровни обработки 4 → 0 по скользящему среднему времени, деградация при отказах прокси (полный → компактный → минимальный → короткий запрос), адаптивное ограничение параллельности при 429, общий cooldown с `Retry-After`, ожидание модели перед стартом, предохранитель при серии ошибок, повторные проходы по неотвеченным вопросам.
- **Отладка:** `SOLUTION_DEBUG=1` пишет `debug.jsonl` с контекстом и черновиками.

Всё это работает и дало результат на лидерборде. **Это не нужно переписывать заново — это нужно сохранить и аккуратно разложить.**

## 7. Этап 3+: доработки

Доработки вводятся **строго по одной и в указанном порядке**, каждая — по протоколу эксперимента (раздел 8.3): гипотеза до запуска → реализация за флагом → замер → отчёт → **остановка и решение пользователя** → только потом следующая. Каждая следующая доработка меряется поверх уже принятых. Нельзя объединять несколько доработок в один замер и нельзя начинать следующую, пока пользователь не принял или не отклонил предыдущую.

Для каждой доработки ниже указаны целевая метрика (что должно улучшиться) и защитные метрики (что не должно ухудшиться).

**Порядок выполнения:** 7.5 (probe — ответы не меняет, нужен для первого пробного сабмита) → 7.6 (few-shot) → 7.1 → 7.2 → 7.3 → 7.4 → 7.7. Few-shot идёт первым, потому что влияет на каждый последующий замер: пока в системном промпте демо-вопросы с готовыми ответами, все доработки меряются на конфигурации, «знающей» часть тестового набора. Нумерация разделов ниже — по смыслу, а не по порядку выполнения.

### 7.1. Проверка номеров пунктов и документов (`checks.py`)
- Каждая ссылка в ответе вида «п. 3.2», «пп. 1–3», «ч. 2», «ст. 164» — проверить, что такой пункт есть в документе, который упоминается рядом (ближайшее упоминание документа по тексту ответа), а если документ неясен — хотя бы в одном документе контекста.
- Номера документов (`А-08/2024`, `К-12`, `ЮО-7`, `152-ФЗ`) — есть в базе.
- Неподтверждённые — в общий список ошибок для вызова исправления; если исправление не помогло — удалить предложение, как сейчас делается для сроков.
- **Цель:** доля ответов с выдуманными пунктами и документами ↓, итоговый балл ↑. **Защита:** доля ложных отказов, полнота ответов, время p95. Дополнительно — точность самой проверки на размеченном наборе ответов с верными и выдуманными ссылками (ложные срабатывания удаляют верные предложения).

### 7.2. Готовый индекс (`index.py`, `tools/build_index.py`)
- Эмбеддинги фрагментов считаются заранее и кладутся в корень: векторы float32 → `array.tobytes()` → base64 в `index_vectors.json`, плюс SHA-256 базы, модель эмбеддингов и размерность.
- При старте: хеш и размерность совпали — загрузка за доли секунды; не совпали — текущий путь v1.3 (расчёт при запуске).
- Экономит до минуты на каждом прогоне.
- **Цель:** время старта ↓. **Защита:** ответы не меняются — на заглушках golden master совпадает байт в байт, на реальной модели итоговый балл в пределах шума.

### 7.3. Даты доп. соглашений и писем (`kb.py`, `dates.py`)
- Извлекать дату начала действия у документов, которые меняют или дополняют другие («с 21.04.2025», «спецификации, подписанные после 01.10.2024») и учитывать их в справке по датам с условием применения.
- Для пунктов законов с пометкой «изменен с <дата>» — если дата события раньше, добавлять в справку: «в базе только действующая редакция ст. N, п. M; на дату события могла действовать иная».
- **Цель:** балл на вопросах типа «дата и редакция» ↑. **Защита:** балл на остальных типах, время p95.

### 7.4. Структурированный результат (`pipeline.py`)
Нужен для интеграции с веб-частью (раздел 9). **Ответ для CSV не менять.** Статус и цитаты вычислять по готовому тексту:
- цитаты — разбором ссылок в ответе и сопоставлением с фрагментами базы (документ, пункт, смещения для подсветки);
- статус (`answer` / `partial` / `no_info` / `premise_error` / `clarify` / `out_of_scope`) — правилами по формулировкам ответа; проверь точность на golden set.
- **Цель:** точность статуса и цитат на размеченном golden set. **Защита:** тексты ответов для CSV не изменились (golden master).

### 7.5. Проверка платформы (`probe.py`)
Дополнить то, что уже есть: хеш найденной базы и совпадение с готовым индексом, размерность эмбеддингов, формат ответа `/rerank` (поля, есть ли скор, тип и диапазон), значения `MAX_WORKERS` и прочих параметров, число вопросов и доля диалогов. В конце прогона — статистика: число вызовов по типам, p50 и p95 задержек, 429, 5xx, таймауты, уровни обработки, сработавшие исправления.
- Вывод — два JSON-блока в stderr: `=== PLATFORM PROBE ===` и `=== RUN STATS ===`. Без ключей, адреса прокси, текстов вопросов и документов.
- У тебя нет доступа к платформе: подготовь сабмит и попроси пользователя прислать stderr из логов платформы. Выводы — в `docs/platform_facts.md`.
- **Защита:** ответы не меняются (golden master), время старта выросло не больше чем на 30 с.

### 7.6. Few-shot примеры (`prompts.py`)
**Выполняется первым из доработок.** Сейчас 8 примеров взяты из демо-вопросов с готовыми ответами. Это искажает оценку на демо-вопросах, может завышать публичный лидерборд относительно закрытого набора и подталкивать модель переносить факты из примеров в ответы на другие вопросы.
- Подготовь альтернативный набор примеров на **вымышленных** документах и законах (те же типы ситуаций: факт из договора, нет в базе, ложная предпосылка, редакция на дату, неоднозначность, диалог, частичный ответ). Вымышленные названия, номера, суммы и сроки не должны совпадать с реальными из базы, чтобы модель не могла их перепутать.
- Отдельно проверь перенос фактов: есть ли в ответах на вопросы вне few-shot числа, пункты или формулировки, которые встречаются только в примерах.
- Сравни варианты **только на вопросах, которых нет среди few-shot**. Решение — за пользователем; покажи цифры.
- **Цель:** балл на вопросах вне few-shot ↑ или без изменений (тогда выигрыш — честность оценки). **Защита:** доля выдуманных фактов, длина ответов.

### 7.7. Вызов анализа запроса — только как эксперимент
Отдельный предварительный вызов LLM (самостоятельная переформулировка вопроса, переписанные поисковые запросы, утверждения пользователя для сверки, флаги injection и противоправности) — за флагом. Включать, только если прирост качества оправдывает дополнительное время (скорость — 15% экспертной оценки, а прогон ограничен 20 минутами).
- **Цель:** балл на диалогах, бытовых формулировках, ложных предпосылках, injection ↑. **Защита:** время p50 и p95 (оценить, уложится ли прогон 200 вопросов в 17 минут при `MAX_WORKERS=2`), число вызовов LLM на вопрос.

## 8. Оценка

### 8.1. Golden set (`eval/golden.csv`)
Поля: `id`, `question`, `expected`, `type` (тип проверки), `docs` (ожидаемые документы и пункты), `in_fewshot` (да/нет), `split` (`dev` / `holdout`).

**Разбиение dev / holdout.** Примерно 60% вопросов — `dev`: на них можно смотреть, разбирать ошибки и подбирать промпты. Остальные — `holdout`: их ответы и ошибки при разработке не разбираются, они только для решения «принять / отклонить». Разбиение — стратифицированное по `type`, фиксируется один раз. Демо-вопросы, попавшие в few-shot, в holdout не входят.

### 8.2. Инструменты (`tools/eval.py`)
- Прогон текущей версии, `tools/baseline/solution_v1_3.py` и стартового примера организаторов (как baseline судьи) на golden set.
- Локальный LLM-судья по правилам регламента: парное сравнение со стартовым примером в двух порядках A/B, шкала 0 / 0,25 / 0,5 / 0,75 / 1, «выдуманный факт = 0». Итог = 0,7 × Match Rate + 0,3 × Win Rate.
- Отдельно: доля ответов с выдуманными числами, пунктами и документами; доля ложных отказов; время на вопрос (среднее, p95); число вызовов LLM на вопрос.
- Метрики считать **отдельно для вопросов из few-shot и для остальных, для dev и holdout, по каждому `type`**.
- **Основная метрика для всех решений «принять / отклонить» — итоговый балл на вопросах вне few-shot.** Балл на всём наборе показывается справочно. Пока few-shot содержит демо-вопросы, вопросы из few-shot в решениях не учитываются.
- Отчёт — `eval/reports/<дата>_<эксперимент>.md` со сравнением с предыдущей принятой версией и с v1.3.

**Измерительный стенд фиксируется до первой доработки** и описывается в `eval/stand.md`:
- версия golden set (хеш файла) и разбиение;
- модель и провайдер генерации, `TEMPERATURE` (как на платформе, по умолчанию 0), `MAX_TOKENS`, `MAX_WORKERS`. Для разработки используется OpenAI-совместимый провайдер из `.env` с теми же идентификаторами моделей, что на платформе. Если провайдер — агрегатор (например, OpenRouter), закрепи конкретного хостера модели через дополнительные параметры запроса, которые задаются **только** переменной окружения для разработки (например, `DEV_EXTRA_BODY`) и никогда не попадают в запросы на платформе;
- модель судьи и текст промпта судьи. **Судья — одна и та же модель на весь хакатон.** По умолчанию — та же DeepSeek V4.1 Flash (дёшево; оба сравниваемых ответа сгенерированы ею же, поэтому предпочтение собственных ответов действует на обе стороны). Другую модель судьи — только по решению пользователя;
- ответы стартового примера организаторов генерируются **один раз** и кэшируются: baseline судьи не должен меняться между замерами;
- ответы судьи кэшируются по ключу (вопрос, ответ A, ответ B, порядок) — повторная оценка неизменившихся ответов бесплатна и не добавляет шума.

**Экономия на разработке** (всё ниже — только для локальной разработки, включается переменными окружения и никогда не работает на платформе):
- эмбеддинги базы считаются один раз и кэшируются на диске по хешу текста фрагмента; в прогоне эмбеддятся только вопросы;
- ответы `/rerank` кэшируются по хешу (запрос, список документов): реранкер оплачивается, только когда меняется поиск;
- ответы чата кэшируются по хешу полного списка сообщений и параметров. **При калибровке шума и при повторных прогонах для проверки значимости кэш чата выключен**, иначе шум не измерить;
- итерации над промптами и правилами — на `dev`-части; полный прогон golden set — только для решения по эксперименту;
- в отчёте по каждому прогону — число токенов по моделям и оценка стоимости.

**Кэш на стороне провайдера (prefix caching).** DeepSeek автоматически кэширует одинаковое начало запросов, и чтение из кэша стоит в десятки раз дешевле обычного входа. Это работает и на платформе, ускоряя ответ. Кэш срабатывает только на **побайтно одинаковом начале** сообщений, поэтому:
- сохраняй порядок v1.3: системный промпт → строка с датой → документы компании в фиксированном порядке → **только потом** всё, что меняется от вопроса к вопросу (законы, справка по датам, история, вопрос, результаты анализа запроса);
- не вставляй ничего переменного в системный промпт и перед блоком документов компании: ни дату события, ни флаги, ни подсказки по вопросу, ни счётчики, ни время;
- порядок и формат документов компании в полном режиме не зависят от вопроса;
- в вызовах исправления и анализа запроса (если появятся) тоже ставь общую часть в начало;
- в `RUN STATS` и отчётах оценки выводи долю входных токенов, прочитанных из кэша (поля `usage`: у DeepSeek — `prompt_cache_hit_tokens`, у OpenAI-совместимых агрегаторов — `prompt_tokens_details.cached_tokens`; читай оба, если есть). Если доля после доработки заметно упала — это защитная метрика: разберись, что сломало общее начало.

Любое изменение стенда (новые вопросы, другой судья, другой промпт судьи) делает старые цифры несравнимыми: после изменения стенда — заново замерить последнюю принятую версию и записать её отдельной строкой.

### 8.3. Протокол эксперимента

**Шаг 0. Калибровка шума (один раз, до первой доработки).** Прогони v1.3 на всём golden set **3 раза** подряд. Посчитай разброс итогового балла и долю вопросов, у которых ответ или оценка менялись между прогонами. Отдельно — один раз переоцени одни и те же ответы судьёй без кэша, чтобы отделить шум генерации от шума судьи. **Порог значимости** = наибольшая разница итогового балла между одинаковыми прогонами (не меньше 0,02). Запиши его в `eval/stand.md`.

**Для каждой доработки:**
1. **Гипотеза до запуска.** Запиши в `eval/experiments.md`: что меняется, на какие вопросы и типы должно повлиять, целевую метрику и ожидаемое направление, защитные метрики. Править гипотезу после замера нельзя.
2. **Реализация за флагом** в `config.py`, отдельный коммит. Флаг выключен — поведение строго как у последней принятой версии (проверяется golden master на заглушках).
3. **Замер:** прогон с флагом включённым на всём golden set. Если разница с принятой версией близка к порогу — ещё 2 прогона и сравнение средних.
4. **Попарное сравнение по вопросам** с последней принятой версией: сколько вопросов стало лучше, хуже, без изменений; список ухудшившихся с причиной (только по `dev`); какие ответы вообще изменились.
5. **Правило решения** (агент предлагает, решает пользователь):
   - **принять**, если целевая метрика улучшилась больше порога шума на `holdout` или на всём наборе, а защитные метрики не ухудшились: число ответов с выдуманными фактами не выросло, доля ложных отказов не выросла, время p95 позволяет уложить 200 вопросов в 17 минут;
   - **отклонить**, если ухудшилась любая защитная метрика или итоговый балл упал больше порога;
   - **без значимой разницы** — изменение в пределах шума. Тогда решают побочные эффекты: доработки на безопасность (например, проверки ссылок) можно принять, если не ухудшили балл; доработки, добавляющие время и вызовы LLM, — отклонить.
6. **Отчёт и остановка.** Покажи пользователю строку журнала и короткий вывод, **затем остановись и дождись решения**. Принятая доработка: флаг включается по умолчанию, коммит с тегом `exp-NN-accepted`. Отклонённая: флаг остаётся выключенным, код остаётся, причина — в журнале.
7. **Проверка на платформе** — не после каждой доработки, а после 2–3 принятых или после крупной (лимит 5 сабмитов в день). Результат лидерборда — в тот же журнал. Публичная часть лидерборда маленькая и шумная: расхождение с локальной оценкой — повод разобраться, а не повод откатывать по одной цифре.

**Журнал `eval/experiments.md`** — одна строка на замер:

| exp | дата | доработка | коммит | стенд | итог (±разброс) | Match | Win | выдуманные | ложные отказы | p50 / p95, с | вызовов LLM/вопр. | целевая метрика | решение | лидерборд |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|---|

Первая строка — v1.3 после калибровки шума, вторая — v1.3 после рефакторинга (должна совпасть в пределах шума).

Доработки, которые по замыслу не должны менять ответы (рефакторинг, готовый индекс, probe, контракт для веба), проверяются golden master на заглушках и временем; полный замер на модели для них нужен один раз, чтобы подтвердить «в пределах шума».

## 9. Интеграция с веб-частью

Веб-интерфейс (чат, просмотр документов с подсветкой пунктов) делает другой разработчик. Твоя задача — чтобы он мог подключить ядро, **не читая его код и не дублируя логику**: веб-чат и `solution.py` должны давать одинаковые ответы на одинаковые вопросы.

### 9.1. Фасад `assistant.py`

```python
from assistant import LegalAssistant

bot = LegalAssistant()            # конфигурация из окружения; можно передать overrides
bot.warmup()                      # загрузка базы и индекса; возвращает health
res = bot.answer([                # история в формате чата
    {"role": "user", "content": "Подскажите гарантию по договору с «Альфой»."},
    {"role": "assistant", "content": "Уточните: «Альфа-Трейд» или «Альфа-Трейдинг»?"},
    {"role": "user", "content": "«Альфа-Трейдинг». На сколько гарантия?"},
])
res.to_dict()                     # JSON-совместимый словарь по контракту
bot.list_documents()              # каталог документов
bot.get_document(doc_id)          # полный текст документа с разметкой пунктов
bot.health()                      # состояние: база, индекс, доступность моделей
```

Требования:
- `answer()` преобразует историю в формат платформы (`Пользователь: … / Ассистент: …`) и вызывает тот же `pipeline.answer`, что и `solution.py`. Для одного и того же диалога ответ должен совпадать с пакетным режимом. Дополнительно — `answer_text(question_text)` для строки в формате платформы.
- **Режим `web`:** нет общего дедлайна и пакетного выбора уровней — всегда полный уровень обработки; таймаут на один ответ (по умолчанию 60 с, настраивается); флаги деградации (например, отключённый реранкер) не залипают навсегда — повторная проверка через заданный интервал.
- **Потокобезопасность:** несколько одновременных `answer()` из разных потоков; база и индекс загружаются один раз и только читаются.
- **Без исключений наружу:** любая ошибка → `Result` со статусом `error`, безопасным текстом и кодом причины в `warnings`.
- Необязательный параметр `on_stage(stage: str)` — колбэк для индикации этапов в интерфейсе (`search`, `generate`, `verify`).
- Только стандартная библиотека и `httpx`: веб-часть может использовать любые фреймворки, но ядро от них не зависит.

### 9.2. JSON-контракт

Опиши контракт в `docs/integration.md` с явной версией `CONTRACT_VERSION` (константа в `assistant.py`). Минимальный состав:

**Ответ (`Result.to_dict()`):**
```json
{
  "contract_version": "1.0",
  "status": "answer | partial | no_info | premise_error | clarify | out_of_scope | error",
  "text": "Итоговый ответ (тот же, что в submission.csv)",
  "citations": [
    {"doc_id": "dogovor-a-08-2024", "doc_title": "Договор аренды № А-08/2024 с ООО «Северный Склад»",
     "doc_kind": "company | law", "clause": "3.1", "quote": "Арендная плата составляет 450 000 …",
     "start": 1834, "end": 1910, "applies_to_event_date": true}
  ],
  "warnings": [{"code": "edition_note", "message": "Применена редакция от 10.01.2023"}],
  "timing_ms": {"search": 120, "generate": 6400, "verify": 15, "total": 6600},
  "debug": {}
}
```

**Каталог (`list_documents()`):** `doc_id`, название, вид (`company` / `law`), тип (договор, доп. соглашение, регламент, письмо, записка, статья закона), статус и даты действия, связанные `doc_id`, есть ли вырезанные инструкции.

**Документ (`get_document(doc_id)`):** полный текст для показа, список пунктов (`clause`, `start`, `end`, заголовок), пометки редакции (для законов), вырезанные встроенные инструкции (позиции и пометка «не является положением документа»), связанные документы.

Обязательные свойства:
- **`doc_id` стабилен** между запусками и сборками индекса (детерминированный slug из пути файла).
- **Смещения согласованы:** `start` и `end` в цитатах и пунктах указывают в тот же текст, который возвращает `get_document`; `text[start:end]` совпадает с `quote`.
- `debug` заполняется только при включённой отладке и не содержит ключей.
- Изменения контракта — только с повышением `CONTRACT_VERSION` и записью в `CHANGELOG.md`; несовместимые изменения — с предупреждением пользователю.

### 9.3. Что передать веб-разработчику

- `docs/integration.md`: как импортировать ядро (модули в корне репозитория, `PYTHONPATH`), инициализация и прогрев, примеры вызовов, контракт с описанием всех полей и статусов, переменные окружения, нужные файлы (`index_*.json`, база), время старта и ответа, потребление памяти, потокобезопасность, обработка ошибок, рекомендации по отображению (как показывать статусы, цитаты, пометки о редакции и вырезанные инструкции).
- `docs/contract_examples/`: реальные JSON-ответы фасада на демо-вопросы разных статусов (ответ, нет в базе, ложная предпосылка, редакция на дату, уточнение, диалог), а также примеры `list_documents()` и `get_document()`. Генерировать скриптом, чтобы обновлялись вместе с кодом.
- `tools/ask.py`: CLI для ручной проверки — вопрос или диалог → JSON фасада. Пригодится и тебе, и веб-разработчику.
- `tests/test_contract.py`: соответствие JSON контракту, стабильность `doc_id`, корректность смещений, одинаковость ответа фасада и пакетного режима (на заглушках HTTP), отсутствие исключений наружу.

Если веб-часть уже есть в репозитории и обращается к ядру иначе — **не переделывай её**, а опиши в отчёте расхождения и предложи, как перейти на фасад.

## 12. Правила работы

- Сначала прочитай `solution.py` и материалы целиком, потом меняй код.
- **Поведение v1.3 — точка отсчёта.** Рефакторинг не меняет ответы; доработки — только за флагами и с цифрами.
- **Одна доработка — один эксперимент — одна остановка.** Не объединяй доработки, не начинай следующую до решения пользователя по предыдущей, не меняй гипотезу после замера, не разбирай ошибки на `holdout`.
- Если по ходу эксперимента хочется поправить что-то ещё (промпт, порог, правило поиска) — это отдельный эксперимент со своей строкой в журнале.
- Новые идеи доработок, которых нет в разделе 7, записывай в `eval/backlog.md` с гипотезой и предлагай пользователю после текущего эксперимента; сам их не начинай.
- Код ядра — только стандартная библиотека и `httpx`. Перед каждым коммитом проверяй импорты корневых модулей.
- Маленькие коммиты с понятными сообщениями, по одному логическому изменению.
- Тесты — на `unittest`, без сети, с заглушками HTTP-слоя.
- Промпты — только в `prompts.py`. Любая правка промпта — с прогоном оценки. Всё переменное — после неизменной части запроса (раздел 8.2, «Кэш на стороне провайдера»).
- Не подгоняй решение под демо-вопросы хардкодом: закрытый набор другой.
- Ничего не удаляй без подтверждения пользователя — перемещай в `archive/`.
- **Не пиши и не меняй веб-часть** (сервер, фронтенд, их Docker-файлы и зависимости). Всё, что нужно веб-разработчику от ядра, — через `assistant.py` и `docs/integration.md`.
- Меняешь что-то, что видно через фасад (поля, статусы, `doc_id`, смещения), — обнови контракт, примеры и `CHANGELOG.md` и отметь это в отчёте отдельной строкой: это сигнал для веб-разработчика.
- Никогда не коммить `.env`, ключи, ответы закрытого набора.
- Если требование неясно или противоречит другому — опиши противоречие и выбери вариант, безопасный для балла.
- Сабмиты на платформу ограничены (5 в день): предлагай пользователю загрузку, только когда локальная оценка показывает улучшение, и объясняй, что именно проверяем.
- После каждого этапа — короткий отчёт: что сделано, тесты и метрики, известные проблемы, следующий шаг.
